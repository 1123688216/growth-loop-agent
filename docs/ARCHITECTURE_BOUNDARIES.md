# 框架职责与编排边界

更新日期：2026-09-22。本文是后续开发的架构约束；旧方案中与此冲突的框架分工以本文为准。角色的信息隔离和教学业务规则继续遵循 `AGENT_ROLES.md`。

2026-09-22 接入状态：已绑定的 RAGFlow 文档由 RAG Tool 直接检索，查询 Embedding 由 RAGFlow 知识库的 BGE-M3 配置负责。SQLite 保留权限范围、文档/片段映射和不可变引用快照，快照不重复切片/向量化。旧上传和联网入库仍保留；混合范围旧资料通过 FTS5 补充。实际用户绑定必须明确账号，不能把配置 API Key 当作所有业务用户的资料授权。下文未修改的 09-16 实现描述为历史阶段记录。

## 1. 不可混淆的核心原则

2026-09-23 课节审核契约：业务服务提供原始 lessonScope（标题/目标），模型改写的搜索词不能定义审核标准。现有 TypeScript Evidence Review 按固定要求返回逐项覆盖和可核验引用，业务层校验引用及计算通过状态；门禁决策缓存绑定原始动作和资料模式。此项属于遗留节点内契约修复，不新增编排层；后续 Pydantic AI 迁移必须保持该边界。

> 跨步骤的状态、分支和恢复统一交给 LangGraph；节点内部的模型调用、工具执行和结构化输出交给 Pydantic AI。

这里的“统一”是目标架构约束，不表示现有实现已经完成迁移。不得在交接、README 或简历中将待迁移能力描述为已经落地。

## 2. 职责分工

| 组件 | 负责 | 不负责 |
|---|---|---|
| LangGraph | 跨步骤状态、条件分支、补充轮次、用户确认中断、checkpoint 与恢复路由 | 教学内容本身、输出字段语义正确性 |
| Pydantic AI | 节点内模型调用、受控工具调用循环、依赖注入、结构化输出与有限的格式校验重试 | 另一套跨步骤状态机、用户等待与恢复、绕过流程预算 |
| Pydantic | 数据字段、类型、范围等契约校验 | 判断知识真实性、评分公平性或引用充分性 |
| RAGFlow（新目标底层） | RAG Tool 内部的解析、切片、Embedding 调用、持久化索引与检索 | 学习业务流程、业务用户身份与资料权限、另一套教学回答流程 |
| 业务服务与数据库 | 鉴权、目标资料范围、业务记录、版本、事务、幂等和来源追溯；实际执行受控读写 | 平行维护相同流程的跳转与恢复规则 |
| 前端 | 提交操作、展示状态和详细进度、用户选择 | 决定后台业务步骤是否完成，或独立驱动恢复状态机 |

Tutor、Planner、Examiner 是业务角色，不是框架功能。它们由提示词、允许读取的上下文、工具权限和输入输出契约共同定义。资料相关性与充分性由模型判断结合业务校验实现，不能说成 Pydantic AI 自动提供的能力。

## 3. 执行与恢复规则

- LangGraph state 保存跨节点必需的标识、结果摘要、状态及结果引用；每个节点只构造当前角色所需的输入，不把整个 state 原样送给模型。
- 节点内 Pydantic AI 可以执行有限工具循环和格式修复；补知识轮次、跨步骤重试及用户选择由 LangGraph 管理，不能在 Agent 内再开一套循环突破预算。
- 需要用户确认时，节点将确认请求交给图中断机制；恢复入口重新校验用户归属和输入，不能仅凭 thread ID 获得执行权限。
- 工具由 Pydantic AI 发起调用，不等于允许模型直接操作任意数据库或网络地址。工具包装层继续校验权限、资料范围、参数和安全限制，并委托业务服务执行。
- 有副作用的工具和节点必须使用业务幂等键、操作结果记录及必要事务。checkpoint 不保证外部操作恰好执行一次，恢复时应复用已经确认完成的结果。
- 业务数据仍保存在业务数据库，checkpoint 只负责工作流执行状态；不将课程、评分等业务记录全搬进 checkpoint。
- 格式通过不等于业务通过。引用支持关系、评分与通过状态一致性、题目版本匹配等仍需业务层校验。

## 4. RAG Tool 契约保留

2026-09-16 用户确认转用 RAGFlow。当前部署与接入边界见 [RAGFlow 部署方案](RAGFLOW_DEPLOYMENT.md)；[旧 LlamaIndex 方案](RAG_LLAMA_INDEX_MIGRATION.md)仅保留为历史实现记录，不再代表目标选型。默认业务后端尚未切换。

保留现有 RAG Tool 的调用入口和调用方契约，验证后直接调用 RAGFlow 检索 API，不叠加 LlamaIndex 中转。输入包含查询与受信任的用户/目标资料范围；输出提供相关片段、来源标识和检索状态。不得把用户身份或任意资料访问范围交给模型自由填写。

MinerU 与本地 Qwen Embedding 后续作为 RAGFlow 的外部服务接入，不重复下载模型。入库与查询使用一致的 Embedding 模型、版本和向量契约。RAGFlow 返回证据，由现有教学角色消费，不再额外启动一套回答生成流程。联网补充的分支、用户选择和恢复归 LangGraph，抓取入库归受控工具及业务服务。

## 5. 当前实现与迁移边界

2026-09-16 新增独立 RAGFlow Docker 配置与启停脚本，未连接模型或替换业务 RAG Tool。以下为旧后端仍然生效的实现状态：

- Python workflow 中已使用 Pydantic AI 生成检索计划、改写搜索词和推荐候选。
- Tutor 与教学证据充分性审核仍主要调用 TypeScript `requestStructured()`；尚未统一迁入 Pydantic AI。
- LlamaIndex 已用于父子切片、本地 Embedding 适配及目标/单资料向量检索。SQLite 保存向量，Node 负责授权快照和落库；Python 分批建立临时内存索引排序。FTS5 和业务证据组装仍在 Node，尚不是独立持久化 RAG 服务。
- Tutor 等模型调用尚待迁移，不宣称所有学习步骤已具备持久化恢复能力。按用户要求本轮只做代码检查，不做真实模型/文件效果验证。

后续按具体链路逐步迁移，保留 API、业务数据与来源 ID。新旧实现切换需有明确入口，不能同时执行两套模型调用或两套流程。替换后更新本节实现状态，废弃路径在回归通过后再处理，不直接清库。

## 6. 后续改动检查清单

- 跨步骤分支、等待和恢复是否由 LangGraph 唯一管理？
- 节点是否仅接收必要上下文？结构化模型调用是否走 Pydantic AI，遗留例外是否注明？
- Agent 内重试是否有限，是否可能与图重试叠加重复执行？
- 工具是否保留权限、范围、幂等和来源追溯？
- RAG Tool 接口是否稳定，入库与查询是否使用一致向量契约？
- 是否测试结构化输出异常、用户中断恢复、恢复后不重复写入和跨用户拒绝访问？
- 是否区分“目标设计”和“已验证实现”，并更新 README 与本文状态？
